FairShare architecture

Design date: October 2, 2026. Based on the completed M1 document, pages 2–4. This document describes the implemented MVP and identifies future work separately. VPS deployment was completed on October 3, 2026.

1. Product and constraints

FairShare helps students turn a course milestone into understandable tasks, agree on workload, and make obstacles visible early. The main workflow is milestone → tasks with context → availability and skills → recommendation → discussion and approval → work → result.

Observations in the product vision PDF come from the team's previous projects. Acceptance of the algorithm and the accuracy of hour estimates remain hypotheses. Neither hours nor activity counts are objective measures of contribution. Avoiding public inactivity rankings, automated grades, and accusations is a product decision, rather than a database limitation.

The initial working assumption is small student teams, several parallel projects, and a single weekly planning interval. Scale limits have not been validated through load testing.

3. Architectural style

A modular monolith: one server process, one relational database, and several functional modules. This suits a team of two or three developers. Distributed transactions, separate queues, and microservice contract coordination would add little value at this stage.

The implementation uses separation of concerns, typed boundaries, UI composition, an independent domain algorithm, a shared Sql/Database port, transactional workflows, optimistic locking for tasks, and explicit authorization. Calling this a strict Clean Architecture implementation would be inaccurate: SQL and application workflows sit alongside HTTP handlers inside feature modules. As the system grows, they can move into application/ and repositories/ while preserving the HTTP contract and domain function.

Membership, availability, and existing assignments are shared across projects. Team and user records are locked before changes; user locks follow a stable UUID order to reduce deadlock risk. Availability updates lock the user's record. Approval rereads the snapshot under those locks. Protection is enforced by the server regardless of the client button's state.

The snapshot includes milestone revision, task IDs and versions, team membership, skills, available hours, and workload. A change to another project's task in the same week changes workload, invalidating an earlier proposal. Approving an already approved proposal returns success without assigning tasks again: the operation is idempotent.

6. Client architecture

App coordinates sessions and project/milestone selection; AppShell handles navigation. The board, workload, team, personal tasks, and activity log are separate feature components. Shared Modal, Button, Avatar, and Progress components provide consistent behavior.

The API client uses same-origin cookies. Saved data is reread from the server, avoiding disagreement between an optimistic interface and server authorization. A request counter protects the main workspace against stale responses when switching projects. A larger version should use TanStack Query with keys such as [projectId, milestoneId], request cancellation, deduplication, and centralized invalidation.

Drag-and-drop is not required: task status changes through an accessible form. Keyboard controls, dialog focus handling, Escape dismissal, mobile layout, text contrast, and reduced motion are supported. These are implemented measures; a separate audit is required before claiming full WCAG certification.

7. Hosting and growth

Locally, one Node process serves the React build and API; PGlite stores data on disk. Do not open a PGlite directory from several processes or place it on ephemeral hosting storage.

The deployed VPS runs the static build and Node API behind Nginx HTTPS, with separate PostgreSQL, a dedicated application account, systemd startup/recovery, daily backups, and a tested release rollback. See VPS operations.

For a pilot, maintain separate demo/staging/production environments and manage environment secrets. Keeping React and the API on one origin reduces cookie and CORS complexity. Hosting providers remain independent of the product domain.

Horizontal scaling first requires regular PostgreSQL, shared rate limiting, and consistent session rules. Push synchronization can use SSE/WebSocket with membership checks and a durable event cursor. If email or notifications are added, save the event and an outbox entry in one transaction; a worker delivers them with retries. Redis becomes useful when queue or presence demand is established. Kubernetes is not a launch requirement.

8. Non-functional targets and current boundaries

Pilot targets, not validated load measurements: ordinary API p95 below 500 ms with 50 active users; allocation of 100 tasks across 10 members within one second; synchronization of other users' changes within 15 seconds plus network latency; production database recovery within four hours, with up to 24 hours of data loss under daily backups.

Implemented capabilities include transactional approval, version checks, membership authorization, sessions, activity history, VPS hosting, and tested database backup restoration. Password recovery, email verification, file storage, email/push delivery, comprehensive versioned migrations for an existing production database, individual member approval of assignments, and multi-instance infrastructure remain future work. They are described in the roadmap.

Product boundary

A full messenger, IDE, automatic code grading, mandatory daily timesheets, public inactivity rankings, and academic grading are outside FairShare's scope. Contextual discussions support task completion; the team's main chat can remain in its existing tool.

Recommended order after the MVP: individual acceptance → handoffs → peer review → notifications → templates. Add complex integrations when demand is observed, so the application does not increase administrative work.

Explainable workload allocation

Inputs and the definition of fairness

Planning covers one week starting on Monday UTC. capacity(member, week) is the number of hours the member declares for all projects in that week, rather than a separate budget for each project. Missing availability is treated as zero: the application does not invent free time.

load(member, week) is the sum of estimates for the member's assigned, unfinished tasks in milestones for that week. Completed task counts, page views, and comments are not used as contribution scores. A blocked task continues to consume planned hours until the team moves or changes it.

The workload ratio is r = planned_hours / declared_hours. For example, six out of six hours means full capacity, while six out of twelve means half capacity. Equal absolute hours or card counts would produce a different, less appropriate allocation.

Implemented MVP algorithm

1. Consider only planned tasks in the selected milestone. Work in progress keeps its assignee; completed tasks are excluded.

2. Subtract the existing assignments of those planned tasks from total workload, so recalculating a milestone does not count them twice.

3. Find eligible members for each task: positive availability and the required skill. The “Any skill” category skips the skill check.

4. Sort tasks by the fewest eligible members, then the largest estimate, then UUID. This protects scarce-skill tasks from earlier consumption of the capacity they need.

5. Exclude members who would exceed availability if assigned the entire task. The algorithm cannot partially assign an indivisible task.

6. Choose the smallest projected ratio (existing_load + task_estimate) / capacity. Break ties using a stable UUID order.

7. If no member is eligible, leave the task unassigned and explain whether the problem is a missing skill or insufficient hours.

8. Show projected workload and assignment reasons. Save the proposal and input snapshot. Actual assignments remain unchanged until approval.

9. The coordinator approves the recommendation after team discussion. This is not individual digital consent from every member; that mechanism is planned for a later version.

The function is in server/allocation.ts and has no database or HTTP dependency. The current straightforward implementation has approximately O(T × M log M + T log T) complexity plus linear passes, which is adequate for small teams.

Exceptions and uncertainty

- Pairing, learning support, or splitting tasks could help when skills are missing. These are useful future features. The MVP exposes the issue and leaves the decision to the team.

- Existing overcommitment remains visible; the algorithm does not assign additional tasks beyond available hours.

- Manual assignment can override restrictions only after explicit coordinator confirmation; the exception is recorded in the activity log.

- Hour estimates are unreliable. A later version should add ranges, confidence, team review, and reserves. Declared estimates must not be treated automatically as actual working time.

- Dependencies determine start/completion order, not a precise schedule within the week. The algorithm does not verify critical paths or calendar feasibility.

- A greedy heuristic can leave a task unassigned even when another order would yield a feasible plan. Larger teams could compare it with integer programming or CP-SAT; an optimizer is not implemented.

Consistency

All assignment changes are approved in a single transaction. External PostgreSQL uses team and member row locks; tasks also carry a version in the UI. A proposal signature includes tasks, workloads, hours, and skills. A mismatch returns HTTP 409. Reapproving an approved proposal does not reassign anything.

Tests cover zero availability, missing skills, other-project workload, preservation of work in progress, prevention of double counting, scarce skills, large indivisible tasks, different hours-to-availability ratios, and deterministic results.

Task states

planned → in_progress → done. A task can return to planning or be completed directly if it has an assignee, its dependency is complete, and a result is described. Completion requires at least 10 characters of evidence text/link and no outstanding help request. Reopening a completed task requires availability checks. Help is a separate field and does not obscure the main status.

started_at records the declared start, first_evidence_at the first result description/link, and done_at completion. These are technical events; they do not automatically prove meaningful work.

The server checks membership on every request. Knowing a UUID does not grant access. An object outside the user's team returns 404; a prohibited action returns 403. There is no superuser role in the user-facing API.

Implemented protections

- Passwords use individual salts and scrypt. Plaintext passwords are not stored in the database or logs.

- Sessions use 32 random bytes, stored as SHA-256 hashes, and expire after seven days. Cookies are HttpOnly/SameSite=Strict, with Secure enabled in production. Logout deletes the server session.

- Mutating requests check Origin and Sec-Fetch-Site; production requires the exact APP_ORIGIN. Arbitrary CORS is not enabled.

- Zod validation, parameterized SQL, and a 100 KB body limit. Login and registration are limited to 12 requests per minute per IP within the current process.

- Only the loopback reverse proxy is trusted to supply client IPs. The deployed application listens on localhost behind Nginx.

- React escapes text. Shared links accept HTTP/HTTPS and open with noopener/noreferrer.

- API responses use no-store. Static responses include CSP, nosniff, no-referrer, and iframe DENY protections.

- Invitations are single-use, valid for 24 hours, and stored as hashes. Sharing an invitation remains the user's action.

- Tasks carry versions; allocation approval is atomic and validates the snapshot signature. Team and member records are locked in a stable order.

- NODE_ENV=production disables demo login by default. Removing the route does not delete educational accounts: an external pilot needs a separate clean database.

Before a broader external pilot

Email verification, password recovery, retention/deletion policies, comprehensive error monitoring, versioned migrations, and separate runtime/migration credentials remain future work. The current schema creates tables idempotently; it is not a complete production schema evolution mechanism.

VPS backups and restoration were implemented and verified on October 3, 2026. Daily backups include the PostgreSQL dump, source, configuration, and checksums. A full restore was tested in a separate database. See the VPS guide for retention and download procedures.

If Supabase is selected as the database provider, disable its Data API for server-owned tables and client-role grants, or use a non-exposed schema. Exposed tables require RLS. Service/secret keys must never be included in React. This application protects data through API checks; the client does not access the database directly. Supabase Auth is not integrated.

Multiple API processes require regular PostgreSQL, shared rate limiting, and concurrency lock verification. PGlite is intended for a single process; do not open the same directory from two servers or store it on ephemeral hosting storage.

Retention and operations

The MVP does not provide account/project deletion, archiving, or discussion deletion. Session expiry is checked on each request, and expired sessions are removed at startup. Retention controls are part of the roadmap.

/api/health checks database connectivity. The recommended verification pipeline is npm ci → typecheck → test → build; it is not an installed GitHub Actions workflow. Back up local PGlite after a clean process shutdown; moving to regular PostgreSQL requires export/import.

The deployed VPS uses local PostgreSQL and a daily systemd backup timer. Broader hosting can use provider backups plus regular restore tests in a separate environment. Proposed RPO of 24 hours and RTO of four hours are pilot targets, not a measured SLA. VPS measures include key-only SSH, disabled root login, a firewall, fail2ban, automatic security updates without automatic reboots, swap, and log storage limits.

Validating the M1 hypotheses

H1: clear context helps people start work

Participants: two real student teams, four to six students, with voluntary participation. The baseline is a comparable task in their usual chat; the intervention is a three-day milestone with six structured tasks. Members read the goal, first step, and expected deliverable before starting.

“Starting meaningful work” means the first substantive document, draft, or code commit within 48 hours, verified by a researcher. Moving a card to “In progress” alone is insufficient evidence. first_evidence_at helps locate when evidence was attached, while its substance and actual creation time are verified separately.

Measurements: time to the first artifact, the number of “where do I start?” questions, coordinator intervention, and members' ability to describe the first step and deliverable in their own words. The PDF's support criteria are that members start within 48 hours, ask noticeably fewer questions, and understand expectations. Additional thresholds can be agreed in advance, such as a 30% relative decrease in questions; this has not been tested and is not a factual result.

If members remain inactive, investigate skills, schedules, dependencies, and motivation separately. The application cannot compel effort.

H2: recommendations are accepted as a starting agreement

Record how many proposals are shown and approved, manual changes, and explanations for them. Ask which constraints the algorithm considered or missed. A coordinator's click does not prove everyone else's agreement; a brief team interview is needed.

H3: hour estimates are sufficient for planning

Compare the original estimate with a voluntary final effort estimate and qualitative reasons for discrepancies. Do not introduce mandatory daily timesheets. If underestimation is systematic, add ranges, reserves, and peer review of estimates. done_at - started_at measures elapsed calendar time, not actual hours worked.

Reducing administrative work

Measure the time to connect the first member and create the first understandable task. M1 targets initial onboarding below three minutes. Measure the entire project setup path separately: the three-minute target is not a promise for complete system setup.

FairShare visual specification

Reference: diagrams/ui-concept.png, 1536 × 1024. This is an application workspace with an open board, three columns, and a separate right-hand workload area. The reference image shows the original Russian interface. There is no marketing page inside the workspace.

Tokens and geometry

- Main background: cool off-white #f7f8fb; surfaces and sidebar: #ffffff.

- Primary text: #171928; secondary text: #737d96; borders: #e5e8f0.

- Accent: #7056e8; light accent background: #eeebff; help background: #fff5df, text #946018.

- Font: Inter when available, otherwise system sans-serif; distinct sizes for headings, buttons, captions, and fields.

- Milestone heading: 38–40 px, weight 700; interface text: 14–16 px; captions: 12–14 px.

- Navigation: 278 px on a wide screen, 230 px on a laptop; top bar: 64 px; workspace padding: 30 px.

- Card radius: 12 px; button radius: 9 px. Subtle shadows, without gradients or decorative illustrations.

- Lucide icons: 18–22 px, stroke width 1.7–2. The equals sign is a meaningful UI icon; branding remains text.

Additional required states

- Login and registration, with demo mode labeled separately.

- Allocation dialog with explanations and explicit approval.

- Task dialog: goal, first step, deliverable, hour estimate, skill, assignee, dependency, state, help request, and result link/description.

- Project and milestone creation, plus milestone selection when several exist.

- Team view: editing personal availability and skills, and creating single-use invitations.

- Workload view: hour totals and ratios to availability.

- Loading, empty projects, no eligible assignees, stale proposals, and access errors.

These states are necessary functional extensions of the reference. On mobile, navigation moves behind a menu button, the board becomes vertical, and workload moves below it. Dialogs support keyboards: they trap focus, close with Escape, and return focus to their trigger. Visible focus rings are required. Reduced animation respects prefers-reduced-motion.
