По M1 Product Vision · 2 октября 2026

Архитектура FairShare

Проектирование: 2 октября 2026 года. Основание — заполненный M1, страницы 2–4. Документ описывает реализованный MVP и обозначает дальнейшее развитие отдельно.

1. Продукт и ограничения

FairShare помогает студентам распределить учебный этап на понятные задачи, согласовать нагрузку и своевременно показать препятствия. Основная пользовательская цепочка: этап → задачи с контекстом → доступность и навыки → рекомендация → обсуждение и подтверждение → работа → результат.

В PDF наблюдения основаны на прошлых проектах самой команды, а принятие алгоритма и точность оценки часов остаются гипотезами. Нельзя считать часы или число действий объективным вкладом. Отказ от публичных рейтингов «пассивности», автоматических оценок и обвинений — продуктовый выбор, а не ограничение базы.

Рабочее допущение для первой версии: небольшие студенческие команды, несколько параллельных проектов, один недельный интервал планирования. Ограничения масштаба ещё не подтверждены нагрузочным исследованием.

Точные установленные версии зафиксированы package-lock.json. Управляемая PostgreSQL допустима у любого совместимого провайдера. Supabase изучен как вариант PostgreSQL/Auth; текущий код не использует Supabase SDK и не требует Supabase-проекта. Если выбрать его базу, приложение подключается серверным адаптером pg; Data API для этих таблиц должен быть закрыт. Подключение Supabase Auth — отдельная будущая замена модуля Identity, а не реализованная функция.

3. Архитектурный стиль

Модульный монолит: один серверный процесс, одна реляционная база, несколько функциональных модулей. Он подходит команде из 2–3 разработчиков: распределённые транзакции, отдельные очереди и согласование контрактов микросервисов пока не дают полезного результата.

Использованы принцип разделения ответственности, типизированные границы, композиция UI, независимый доменный алгоритм, общий порт базы Sql/Database, транзакционные сценарии, optimistic locking для задач и явная проверка полномочий. Называть MVP строгой реализацией Clean Architecture было бы неточно: SQL и сервисные сценарии находятся рядом с HTTP-обработчиками внутри feature-модулей. При росте их можно вынести в application/ и repositories/, сохранив HTTP-контракт и доменную функцию.

5. Сценарий подтверждения распределения

Исходник схемы Mermaid
sequenceDiagram
  actor L as Координатор
  participant UI as React
  participant API as Fastify
  participant DB as PostgreSQL
  L->>UI: Распределить задачи
  UI->>API: POST allocations
  API->>DB: Проверить членство, заблокировать команду и участников
  API->>DB: Прочитать задачи и недельную нагрузку
  API->>API: Построить объяснимую рекомендацию
  API->>DB: Сохранить предложение и подпись снимка
  API-->>UI: Назначения, причины, предупреждения
  L->>UI: Принять после обсуждения
  UI->>API: POST allocation/approve
  API->>DB: Начать транзакцию, получить блокировки
  API->>API: Сравнить актуальную подпись со снимком
  alt Данные изменились
    API-->>UI: 409 / требуется пересчёт
  else Снимок актуален
    API->>DB: Изменить все назначения, версии и журнал
    API->>DB: COMMIT
    API-->>UI: Принято
  end

Членство, доступность и уже назначенная работа — общий контекст нескольких проектов. Записи команды и пользователей блокируются до изменения; пользователи — в стабильном порядке UUID, чтобы уменьшить риск взаимных блокировок. Доступность пользователя блокирует его запись. Подтверждение повторно читает снимок под блокировками. Защита работает на сервере, независимо от состояния кнопки клиента.

Снимок включает версию этапа, IDs и версии задач, состав команды, навыки, часы доступности и нагрузку. Изменение задачи в другом проекте за ту же неделю изменит нагрузку, поэтому старое предложение также отклоняется. Повторное принятие уже принятого предложения возвращает успех без повторного назначения: идемпотентность.

6. Клиентская архитектура

App координирует сессию, выбор проекта и этапа; AppShell отвечает за навигацию. Доска, нагрузка, команда, личные задачи и журнал — отдельные feature-компоненты. Общие Modal, Button, Avatar, Progress задают единое поведение.

API-клиент использует same-origin cookies. При сохранении данные перечитываются с сервера, что исключает расхождение оптимистичного интерфейса с проверкой прав. Номер запроса защищает основное пространство от устаревшего ответа при переключении проектов. В будущей версии с большим числом экранов нужен TanStack Query: ключи вида [projectId, milestoneId], отмена запросов, дедупликация и централизованная инвалидизация.

Перетаскивание не требуется для управления задачей: статус меняется в доступной форме. Клавиатура, фокус в диалогах, Escape, мобильная компоновка, контраст текста и reduced motion поддерживаются. Это набор реализованных мер; полную сертификацию WCAG без отдельного аудита заявлять нельзя.

7. Размещение и развитие

Локально один Node-процесс раздаёт сборку React и API; PGlite хранит данные на диске. PGlite не следует подключать одновременно к нескольким процессам или держать на временном диске hosting-платформы.

Для пилота: статическая сборка + Node API за HTTPS, управляемая PostgreSQL, секреты окружения, отдельные окружения demo/staging/production. Можно оставить React и API на одном домене: меньше сложностей с cookies и CORS. Провайдер размещения не связан с доменом продукта.

При горизонтальном масштабировании сначала используются обычная PostgreSQL, распределённый rate limit и общие правила сессий. Для push-синхронизации — SSE/WebSocket с проверкой членства и устойчивым курсором событий. Если появятся письма/уведомления, событие и запись outbox сохраняются одной транзакцией, worker доставляет их с повторными попытками. Redis нужен при подтверждённой нагрузке очередей или presence; Kubernetes не является условием запуска.

8. Нефункциональные цели и честные границы

Цели пилота, ещё не подтверждённые нагрузочным измерением: p95 обычного API до 500 мс при 50 активных пользователях; распределение 100 задач между 10 участниками до 1 секунды; синхронизация чужих изменений до 15 секунд плюс сетевое время; восстановление production-базы за 4 часа, допустимая потеря до 24 часов при ежедневной резервной копии.

Реализованы транзакционное принятие, контроль версий, проверки членства, сессии и история. Не реализованы восстановление пароля, проверка email, файловое хранилище, email/push, полноценные versioned migrations для уже существующей production-базы, индивидуальное принятие назначения каждым участником и multi-instance инфраструктура. Эти работы описаны в дорожной карте, а не скрыты за макетом.

Приоритет P3: интеграции

- GitHub/GitLab: прикрепление результата и проверки PR; коммиты не считаются качеством или вкладом.

- Файлы: приватное object storage, лимиты, сканирование, signed URLs.

- Общий календарь дедлайнов, ICS и calendar sync; синхронизация исключена из первой версии M1.

- Telegram/email digest: только по явной подписке участника на канал.

- PWA, offline-чтение и затем конфликтобезопасные offline-изменения.

- AI-черновик разбивки задания с проверкой человеком; AI syllabus parsing исключён из первой версии M1.

- Обезличенные продуктовые метрики для проверки гипотез, без публичного рейтинга студентов.

- CP-SAT/целочисленный оптимизатор, когда жадная эвристика на реальных данных окажется недостаточной.

Граница продукта

Полный мессенджер, IDE, автоматическое оценивание кода, обязательный ежедневный timesheet, публичный рейтинг «пассивности» и выставление учебных оценок не входят в FairShare. Контекстные обсуждения помогают выполнять задачи; основной чат может остаться в привычном инструменте.

Рекомендуемый порядок после MVP: индивидуальное согласие → передача → взаимная проверка → уведомления → шаблоны. Сложные интеграции добавляются после наблюдаемой потребности, чтобы приложение не увеличивало административную нагрузку.

Объяснимое распределение нагрузки

Данные и определение справедливости

Планируется одна неделя, начинающаяся в понедельник UTC. capacity(member, week) — заявленные участником часы для всех проектов за эту неделю. Не число часов в каждом отдельном проекте. Отсутствующая декларация считается нулём: приложение не придумывает свободное время.

load(member, week) — сумма оценок всех назначенных, незавершённых задач участника в этапах этой недели. Число завершённых задач, просмотры и комментарии не используются как оценка вклада. Заблокированная задача продолжает занимать плановые часы, пока команда не перенесёт или не изменит её.

Коэффициент загрузки: r = planned_hours / declared_hours. Например, 6 из 6 часов — полная загрузка; 6 из 12 — половина. Равные абсолютные часы или количество карточек дали бы другое, менее подходящее распределение.

Алгоритм реализованного MVP

1. Берём только planned задачи выбранного этапа. Начатые задачи сохраняют исполнителя. Завершённые не участвуют.

2. Из общей текущей нагрузки вычитаем назначения этих же запланированных задач, чтобы пересчитываемый этап не учитывался дважды.

3. Для каждой задачи определяем допустимых участников: доступность больше нуля и наличие обязательного навыка. Для «Любой навык» проверка навыка не нужна.

4. Сортируем задачи: сначала меньше подходящих участников, затем больше часов, затем UUID. Это защищает задачи с редким навыком от раннего расходования нужной ёмкости.

5. Исключаем участников, для которых задача целиком приведёт к превышению доступности. Частично назначать неделимую задачу алгоритм не умеет.

6. Выбираем минимальное прогнозируемое отношение (existing_load + task_estimate) / capacity. При равенстве — стабильный UUID.

7. Если участника нет, оставляем задачу без назначения и объясняем: нет навыка или нет свободных часов.

8. Показываем будущую нагрузку и причины назначений. Записываем предложение и снимок входных данных. До подтверждения реальные назначения не меняются.

9. Координатор подтверждает рекомендацию после командного обсуждения. Это не индивидуальные цифровые согласия всех участников; такой механизм предусмотрен следующей версией.

Функция находится в server/allocation.ts, не зависит от базы и HTTP. Сложность текущей простой реализации — приблизительно O(T × M log M + T log T) с дополнительными линейными проходами; для малых команд её достаточно.

Исключения и неопределённость

- При нехватке навыков предложить парную работу, обучение или разбивку задачи — полезная следующая функция. MVP показывает проблему и оставляет решение команде.

- При перегрузке уже принятой работой алгоритм не скрывает её и не добавляет новые задачи сверх часов.

- Ручное назначение может нарушить ограничения только после явного подтверждения координатором; факт исключения записывается в журнал.

- Оценка часов ненадёжна. В следующей версии нужны интервалы, уверенность, командная проверка оценок и резерв. Не следует автоматически считать заявленные часы истинным временем выполнения.

- Зависимость определяет порядок начала/завершения, но не точное расписание внутри недели. Алгоритм не проверяет критический путь и календарную выполнимость цепочки.

- Жадная эвристика может оставить задачу без участника, хотя другой порядок назначений дал бы допустимый план. Для более крупных команд можно сравнить её с integer programming или CP-SAT; оптимизатор пока не реализован.

Согласованность

Все изменения назначений принимаются одной транзакцией. Внешняя PostgreSQL использует блокировки команды и записей участников; задачи в UI дополнительно имеют version. Подпись предложения включает задачи, нагрузки, часы и навыки. Несовпадение возвращает HTTP 409. Повторное подтверждение принятого предложения ничего не переназначает.

Тестируются нулевая доступность, отсутствие навыка, нагрузка других проектов, сохранение начатой работы, отсутствие двойного счёта, редкие навыки, большие неделимые задачи, разные отношения часов к доступности и повторяемость результата.

Состояния задачи

planned → in_progress → done. Можно вернуть задачу в план или сразу завершить её, если есть исполнитель, завершена зависимость и описан результат. Для завершения нужен текст/ссылка от 10 символов и снятый запрос помощи. Повторное открытие завершённой задачи требует проверки доступности. Help — отдельное поле, которое не скрывает основной статус.

started_at означает заявленное начало, first_evidence_at — первое описание/ссылку, done_at — завершение. Это технические события, которые не доказывают содержательность работы автоматически.

Сервер проверяет членство на каждом запросе. UUID не даёт доступ. Объект вне своей команды возвращает 404; запрещённое действие — 403. Отдельного суперпользователя в пользовательском API нет.

Реализованная защита

- Пароли: индивидуальная соль и scrypt. В БД и логах нет открытых паролей.

- Сессия: 32 случайных байта, в БД SHA-256-хэш, срок 7 дней. Cookie HttpOnly/SameSite=Strict, в production Secure. Выход удаляет серверную сессию.

- Проверка Origin и Sec-Fetch-Site на изменяющих запросах; в production точный APP_ORIGIN. Произвольный CORS не включён.

- Zod, параметризованный SQL, тело до 100 KB. Вход/регистрация ограничены 12 запросами в минуту на IP текущего процесса.

- React экранирует текст. Общие ссылки принимают HTTP/HTTPS, открываются с noopener/noreferrer.

- API: no-store. Статические ответы: CSP, nosniff, no-referrer, DENY iframe.

- Приглашения одноразовые, 24 часа, хранятся хэши. Отправка остаётся действием пользователя.

- Задачи имеют version; принятие распределения атомарно и проверяет подпись снимка. Блокируются команда и участники в стабильном порядке.

- NODE_ENV=production отключает демовход по умолчанию. Отключение маршрута не удаляет учебные аккаунты: внешнему пилоту нужна отдельная чистая база.

Перед внешним пилотом

Проверка email, восстановление пароля, политика хранения/удаления, резервные копии с проверенным восстановлением, наблюдения ошибок, versioned migrations и разные учётные данные runtime/migration пока не реализованы. В текущем MVP схема идемпотентно создаёт таблицы; это не полноценный механизм эволюции production-базы.

Если выбрать Supabase-провайдер: закрыть Data API для серверных таблиц и grants клиентских ролей или использовать неэкспонируемую схему. Любые экспонируемые таблицы требуют RLS; service/secret key нельзя помещать в React. В текущем приложении данные защищаются API-проверками, клиент не имеет доступа к БД. Supabase Auth не подключён.

Несколько API-процессов требуют обычной PostgreSQL, общего rate limit и проверки конкурентных блокировок. PGlite предназначена для одного процесса; нельзя одновременно открывать один её каталог двумя серверами или хранить его на временном диске hosting-платформы.

Хранение и эксплуатация

В MVP нет удаления аккаунта/проекта, архива и удаления обсуждения. Просроченные сессии проверяются на каждом запросе и очищаются при старте. Добавление управления сроками хранения входит в дорожную карту.

/api/health проверяет БД. CI: npm ci → typecheck → test → build. Локальную PGlite резервировать после корректного завершения процесса; перенос в обычную PostgreSQL требует экспорта/импорта. Production использует резервные копии PostgreSQL-провайдера и регулярную проверку восстановления в отдельное окружение. Предлагаемые RPO 24 часа и RTO 4 часа — цели пилота, не измеренный SLA.

Проверка гипотез M1

H1: понятный контекст помогает начать работу

Участники: две реальные студенческие команды, 4–6 студентов, добровольное участие. Базовый период — сопоставимая задача в привычном чате; затем трёхдневный этап из шести структурированных задач. Команда читает цель, первый шаг и ожидаемый результат до начала.

«Начало содержательной работы» — первый содержательный документ, черновик или кодовый коммит в пределах 48 часов, проверенный исследователем. Перевод карточки в «В работе» сам по себе этим доказательством не является. first_evidence_at помогает найти момент прикрепления, но содержательность и фактическое время артефакта проверяются отдельно.

Измерения: время до первого артефакта, число вопросов «с чего начать», необходимость вмешательства координатора, способность участника своими словами назвать первый шаг и результат. Условия поддержки гипотезы из PDF: участники начинают в пределах 48 часов, вопросов заметно меньше, ожидания понятны. Дополнительный порог можно согласовать заранее, например относительное снижение вопросов на 30%; он ещё не проверен и не является фактом.

Если участники продолжают бездействовать, исследовать отдельно навыки, расписание, зависимости и мотивацию. Приложение не может принудить к усилию.

H2: рекомендации принимаются как исходная договорённость

Записать число показанных и принятых предложений, ручные изменения и их объяснения. Спросить участников, какие ограничения алгоритм учёл и чего не учёл. Одно нажатие координатора не доказывает согласие остальных: нужно короткое интервью команды.

H3: оценок часов достаточно для планирования

Сравнить исходную оценку с добровольной итоговой оценкой усилия и качественными причинами отклонения. Не вводить обязательный ежедневный timesheet. При систематической недооценке добавить диапазоны, резерв и взаимную проверку оценок. История done_at - started_at означает календарное время, не количество фактически отработанных часов.

Снижение административной нагрузки

Измерить время подключения первого участника и создания первой понятной задачи; цель M1 для первоначального onboarding — меньше 3 минут. Необходимо отдельно измерить полный путь настройки проекта: три минуты не являются обещанием всей настройки системы.

Индекс Supabase сообщает изменение PostgreSQL minor versions от 25 сентября 2026 года с предупреждением о переиндексации отдельных extensions и legacy-cipher данных. MVP не использует ltree, btree_gist, pgcrypto-шифрование или существующую Supabase-базу; конкретную миграцию чужого проекта не выполняли. Документация signing keys также проверена через официальный поиск Supabase MCP.

Данные задач и имена берутся из API. Счётчики, дата и нагрузка меняются вместе с данными: макет не является источником бизнес-данных.

Дополнительные обязательные состояния

- Вход и регистрация; отдельно обозначенный деморежим.

- Диалог распределения с объяснениями и явным подтверждением.

- Диалог задачи: цель, первый шаг, результат, оценка часов, навык, исполнитель, зависимость, состояние, запрос помощи, ссылка или описание результата.

- Создание проекта и этапа, выбор этапа при нескольких этапах.

- Команда: редактирование собственной доступности и навыков, создание одноразового приглашения.

- Нагрузка: таблица часов и отношения к доступности.

- Обработка загрузки, пустого проекта, отсутствия подходящих участников, устаревшего предложения, ошибок доступа.

Это функционально необходимые продолжения макета. На мобильном экране навигация скрывается за кнопкой меню, доска становится вертикальной; нагрузка располагается ниже. Диалоги доступны с клавиатуры: удерживают фокус, закрываются Escape и возвращают фокус инициатору. Видимый focus-ring обязателен. Уменьшенная анимация учитывает prefers-reduced-motion.
